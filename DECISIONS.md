**Phase 1 progress note (2026-09-22, cross-process alert evaluation):** closed the last remaining item on the known-gaps list - a real ingestion tick (via Redis, a separate CLI process) was relayed to browsers by the SSE route but never triggered alert evaluation server-side, since only the local "Simulate market tick" route called `evaluateAlerts()` directly. The fix that actually works, found the hard way: the first attempt used `instrumentation.ts`, Next's official one-time server-startup hook - the obviously-correct-looking place. It silently didn't work. A real multi-process Redis test (not a guess) proved why: `instrumentation.ts` compiles into its own isolated bundle that does not share a module singleton with route handlers, even within the same running Node.js process - a subscription set up there never received events a route handler's `realtimeBus.publish()` published. Enabling `instrumentationHook` also broke the production build outright in a second, unrelated way: Next compiles `instrumentation.ts` for the Edge runtime too (unconditionally, no per-runtime opt-out in this Next 14.x version), which pulled `ioredis` (Node-only builtins) into that Edge bundle and failed to resolve `net`/`dns`/`crypto`/`stream` - required a `next.config.mjs` `webpack()` override aliasing `ioredis` to `false` for the edge runtime as a workaround, which then became moot once `instrumentation.ts` was abandoned. The actual fix: `lib/alerts/tick-listener.ts`'s `subscribeAlertsToTicks()` is called at **module scope** inside `app/api/v1/stream/route.ts` (not instrumentation.ts) - proven to share module state with other route handlers, since that's the exact mechanism real-time push already relies on, and every authenticated page loads that route via `live-indicator.tsx`'s `EventSource` connection anyway. The old direct `evaluateAlerts()` call in `app/api/v1/simulate-tick/route.ts` was removed to avoid double-evaluating local ticks once the central listener also reacts to them. Live-verified for both paths with real infrastructure, not just unit tests: a two-tab Playwright run confirmed the local path; separately, a genuinely external Node process (via a real Redis container, mimicking the ingestion CLI) published a tick, and a connected browser's alert fired from that remote publish - the exact scenario the gap was about.

## 1. Name & domain

**Preliminary web research (2026-09-20), not a substitute for formal clearance:**

- No sports-betting or gaming-industry trademark for "EdgeHub" turned up in general search.
- There **is** an established, actively-maintained product also named "EdgeHub": [Advantech's EdgeHub](https://www.advantech.com/en-us/products/edgehub/sub_a3e4d4db-6fb1-4809-b621-56f6968ca6bd), an industrial IoT edge-device-management platform (recent releases as of August 2026). Different market/goods class (industrial IoT vs. consumer sports-betting SaaS), so trademark *confusion* risk is likely low, but:
  - It dominates general search results for "EdgeHub," which is a real SEO/branding cost regardless of trademark risk.
  - Advantech is a large, established company - worth knowing they exist before getting attached to the name.
- Adjacent naming crowding in the sports-betting space: "EdgeSports" (Edge Sports LLC, an existing betting app) and "The Edge Systems Technologies LLC" (holds several unrelated "___ Genius" sports marks). Neither is a direct collision, but it confirms "Edge"-prefixed names are common in this category.

**Still required before committing to the name:**
1. A real USPTO search at [tmsearch.uspto.gov](https://tmsearch.uspto.gov/) (or through counsel) - general web search does not reliably surface exact-match trademark registrations.
2. Domain availability check for `edgehub.com` / `.io` / `.app` / `getedgehub.com` at an actual registrar (Namecheap/GoDaddy/etc.) - general search couldn't confirm live availability either way.
3. A decision on whether the Advantech collision (search-visibility, not legal) is acceptable or worth avoiding via a name variant.

**Recommendation:** don't block engineering on this - the codebase already treats "EdgeHub" as a working name per the PRD's own framing. Resolve it in parallel with Phase 0 items 3-4 (counsel engagement) since a trademark attorney doing formal clearance can check the name at the same time.
